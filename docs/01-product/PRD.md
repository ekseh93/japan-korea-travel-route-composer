# 제품 요구사항 문서

> 상태: 설계 승인
> 작성일: 2026-08-15
> 담당: 5.6 Sol
> 구현 상태: 미구현
> 업무·시스템 요건 기준선: [요건정의서](REQUIREMENTS_DEFINITION.md)

이 문서는 제품 문제·사용자·가치·MVP를 정의한다. 업무 승인, RACI, 업무 규칙,
데이터·연계·운영·전환요건과 변경관리는 요건정의서를 단일 기준으로 사용한다.

## 1. 제품 한 줄 정의

여행 조건을 입력하고 조합하기를 누르면 도쿄 또는 서울의 이동 낭비를 줄인
일자별 일정과 추천 근거를 함께 제공하는 출처 기반 여행 동선 조합기다.

## 2. 해결할 문제

여행자는 장소 추천, 실제 경험담, 영업시간, 지도와 이동 경로를 서로 다른
서비스에서 반복 검색한다. 인기 장소만 모으면 하루 안에 소화하기 어려운
왕복 동선이 생기며, AI 답변은 추천 이유와 출처가 분리되거나 최신성을
확인하기 어렵다.

이 제품은 장소를 많이 보여주는 대신 사용자의 제약 안에서 방문 가능한
장소를 골라 하루 단위로 묶고, 각 추천의 근거와 확인 날짜를 결과 안에서
검증할 수 있게 한다.

## 3. 목표 사용자

| 사용자 | 상황 | 필요한 결과 |
|---|---|---|
| 첫 자유여행자 | 지역 감각과 환승 경험이 부족함 | 무리 없는 기본 동선과 이유 |
| 재방문 여행자 | 유명 관광지보다 테마가 중요함 | 감성, 쇼핑, 음식 등 취향 중심 조합 |
| 가족 여행자 | 보행량과 휴식이 중요함 | 낮은 이동 부담과 휴식 가능한 일정 |
| 친구 여행자 | 여러 관심사를 절충해야 함 | 테마 다양성과 재조합 가능성 |

## 4. 핵심 JTBD

- 여행 조건을 정했을 때 직접 장소를 나열하지 않고 실행 가능한 하루 일정을 받고 싶다.
- 추천 장소가 왜 선택됐고 어떤 출처로 확인됐는지 즉시 알고 싶다.
- 마음에 들지 않는 일정은 필수 장소를 유지한 채 다른 유효 조합으로 바꾸고 싶다.
- 실제 이동 시에는 원본 지도 서비스에서 경로를 다시 확인하고 싶다.

## 5. 가치 제안

1. 출처 투명성: 추천 카드마다 공식 정보, 근거 유형, 확인 날짜와 링크를 표시한다.
2. 동선 효율: 지역 군집, 이동시간, 영업시간과 체류시간을 함께 계산한다.
3. 설명 가능성: 총점뿐 아니라 선택 이유와 제외 이유를 사용자 언어로 설명한다.
4. 안전한 데이터: 허가된 공개 데이터와 직접 작성한 요약만 게시한다.
5. 재현 가능성: 같은 입력과 데이터 버전은 같은 기본 결과를 만든다.

## 6. MVP 범위

### 포함

- 도쿄와 서울
- 1~4박 일정
- 여행 도시, 시작일, 1~4박, 도착·출발 시간
- 동행 유형, 관심 테마, 예산, 여행 속도, 걷기 허용량
- 필수 방문 장소와 제외 장소
- 일자별 장소, 체류시간, 예상 이동시간, 휴식 구간
- 추천 이유, 근거 등급, 출처 링크, 마지막 확인일
- 지도 마커와 외부 길찾기 링크
- 유효한 상위 후보 안에서 새 조합 생성
- 오류 제보와 출처 정정 요청 링크
- 한국어 UI 우선, 콘텐츠의 일본어·영어 확장 가능한 구조

### 제외

- 회원가입, 로그인, 개인 일정 영구 저장
- 사용자 리뷰 작성과 커뮤니티
- 예약, 결제, 광고, 제휴 링크
- 가격 비교와 실시간 재고
- 전국 단위 장소 검색
- 외부 커뮤니티 리뷰·사진의 자동 수집
- LLM이 장소나 이동시간을 임의 생성하는 기능
- 실시간 교통 장애를 반영한 내비게이션

## 7. 핵심 사용자 흐름

1. 사용자가 도쿄 또는 서울을 선택한다.
2. 일정과 여행 조건을 입력한다.
3. 조합하기를 누른다.
4. 시스템이 조건을 검증하고 후보 장소를 필터링한다.
5. 지역 군집과 시간 창을 기준으로 실행 가능한 일정을 계산한다.
6. 사용자는 일자별 동선, 추천 이유와 출처를 확인한다.
7. 필요하면 조건을 수정하거나 새 조합을 요청한다.
8. 실제 이동은 외부 지도 링크에서 최신 경로를 확인한다.

## 8. 성공 기준

출시 전 자동·수동 검증으로 판정하며 실제 사용자 수를 가정하지 않는다.

| 기준 | 목표 |
|---|---|
| 출처 완전성 | 공개 추천 장소 100%에 출처, 유형, 확인일 존재 |
| 일정 유효성 | Golden Fixture의 필수 장소·영업시간·일일 시간 예산 위반 0건 |
| 결정성 | 동일 입력·동일 데이터 버전의 기본 결과 해시 일치 |
| 설명 가능성 | 모든 추천에 선택 점수 구성과 최소 1개 근거 표시 |
| 접근성 | 핵심 흐름 WCAG 2.2 AA 자동 검사와 키보드 수동 검사 통과 |
| 비용 안전 | 계정 자격과 예상 비용 확인 전 AWS apply 차단 |
| 복구성 | 로컬 실행과 전체 Terraform destroy 절차 문서화 |

## 9. 제품 원칙

- 추천 수보다 실행 가능성을 우선한다.
- 이동시간은 추정치로 표시하고 외부 지도 확인을 안내한다.
- 후기의 인기도와 공식 사실을 동일한 근거로 취급하지 않는다.
- 근거가 없거나 오래된 장소는 추천 후보에서 제외할 수 있다.
- 새로운 조합은 무작위가 아니라 유효한 상위 후보의 다양화다.
- 수정 요청을 숨기지 않고 출처 카드 가까이에 배치한다.

## 10. 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 외부 데이터 이용 조건 변경 | 게시 중단 또는 재수집 필요 | 출처 레지스트리, 확인일, 비활성화 스위치 |
| 대중교통 API 비용 | 0원 목표 실패 | 기본은 검수된 지역 행렬, 유료 API는 기능 플래그 |
| 영업시간 변경 | 실행 불가능한 일정 | 확인일 표시, 계절·임시휴업 경고, 정정 요청 |
| AI 환각 | 잘못된 추천 이유 | 승인 근거만 입력, 사실 필드는 템플릿 출력 |
| AWS 무료 조건 차이 | 예상치 못한 결제 | 배포 전 체크리스트, 예산 경보, 사용량 제한, 철거 |
| 데이터 검수 과부하 | 출시 지연 | 2개 도시와 150~250개 장소로 제한 |

## 11. 결정, 가정, 미해결 항목

### 결정

- MVP는 도쿄와 서울만 지원한다.
- 계정 없는 공개 조합 기능을 먼저 구현한다.
- 추천과 경로 계산은 결정론적 도메인 로직이 담당한다.
- 외부 커뮤니티 자동 수집은 MVP에서 제외한다.

### 가정

- 초기 장소 데이터는 저장소에서 검수한 Seed로 배포할 수 있다.
- 이동시간은 실시간 내비게이션이 아니라 일정 편성용 추정치로 충분하다.
- CloudFront 기본 도메인으로 공개할 수 있으며 사용자 도메인은 필수가 아니다.

### 구현 전 입력값

- AWS 계정 생성일과 Free/Paid 플랜
- 사용할 GitHub 저장소와 기본 브랜치
- 비용 경보를 받을 이메일
- TourAPI와 선택적 외부 지도 API 키 보유 여부

이 값들은 설계를 막지 않지만 실제 배포 승인의 필수 조건이다.
